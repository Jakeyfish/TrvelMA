# 产品版本与数据边界

## 版本拆分

| 版本 | 数据放置 | 使用方式 | 收费方式建议 |
| --- | --- | --- | --- |
| 单机版 | 只在当前设备的 SwiftData 数据库 | 无需登录、离线可用；提供手动导出/恢复 | 一次性买断 |
| 云端版 | Supabase 账户数据 | 登录后通过网络使用；云端备份 | 月付/年付订阅 |
| 双端同步版 | 同一账户的 Supabase 数据，并缓存到 iOS | iOS 与 Web 使用同一份云端数据；离线修改排队后同步 | 月付/年付订阅的高阶档，或云端版增购项 |

云端同步会持续产生数据库、图片存储、带宽和备份费用，因此不建议把云端能力包含在永久买断里。暂不确定售价、试用期和同步设备数量；先接好权益识别和用量统计，再根据 Supabase 费用决定档位。

## 代码和服务边界

- `LocalDataStore`：单机版读写设备数据库，不能调用网络上传。
- `CloudDataStore`：云端版/同步版访问 Supabase，所有用户记录由 RLS 按 `auth.uid()` 隔离。
- `SyncCoordinator`：仅双端同步版启用，负责离线队列、冲突处理、重试和同步状态。
- `AssetStorage`：头像、名片、收款码、名片二维码等图片放私有对象存储；数据库仅存对象路径和元数据。
- `EntitlementProvider`：从 StoreKit 和服务端校验结果判断 `local`、`cloud`、`sync` 权益。UI 只能展示权益，服务端仍需限制云端 API、Storage 和设备数。
- Web 与 iOS 共用云端数据表和权益规则。不能让 Web 客户端持有 Supabase service-role 密钥。

## 已完成的基础步骤

- 云端账号第一次发现本机资料时，先统计最近一次使用的本机账号资料与旧版未归属资料，再询问默认方式；用户选择后按云端账号记住偏好，可在设置中修改。
- 只有尚未迁移或迁移后又修改过的本机名片、收款方式才会触发确认；云端已有资产不会被误判成本机待上传数据。
- 设备没有待迁移本机资料时直接下载云端内容。
- 可选择自动导入并同步本机资料，或只使用当前云端账号资料；本机原始资料保留在设备上。

- 本机账号按邮箱分配独立范围；用户确认后，只迁入最近一次使用的本机账号资料和旧版未归属记录，其他本机账号资料仍留在设备上。
- SwiftData 持久化模型清单已集中到 `AppDataSchema`，容器工厂可以为相同模型创建不同命名的数据库文件。

SwiftData 现拆成本机与云端缓存两个物理数据库文件；云端缓存仍是设备本地副本，不代表远端网络已连接成功。旧版没有账号归属的数据会先进入本机库，再由用户选择是否导入云端。用户反馈数据测试目前没有问题；这记录为测试设备验收通过，不代表生产数据已迁移。名片与收款图片已接入 Storage 客户端流程；远端开发项目的私有 bucket 和 4 条用户目录访问策略已创建，并已查询确认。

## 版本路线拆分进度

目前认证仍只有“本机账号”和“云端账号”两种身份；代码已增加独立的 `ProductEdition` 能力层，并让双向同步的入口检查同步能力。兼容映射暂时将云端账号解析为 `.sync`，所以现有用户行为不变；单机版的网络隔离也已在同步服务入口加固。接下来应接入真正的权益来源，并实现 `.cloud` 的在线数据访问路线，再决定 StoreKit SKU 与价格。

1. **能力定义已落代码，权益来源待接入**：本机版不调用业务云 API；云端版在线访问云数据；同步版允许本地离线写入、队列重放、冲突解决和多设备数限制。
2. 为 iOS 和 Web 共用同一份权益规则；服务端对云端数据、图片存储和设备数做最终校验，客户端只控制界面与缓存行为。
3. 完成两种云端能力的行为差异和回归核对后，再接 StoreKit 买断/订阅与服务端交易验证。

### 权益服务端契约（2026-10-21）

- 新增 `account_entitlements` 数据表迁移，字段包括账户、版本、权益状态、到期时间、设备上限和更新时间。
- 表启用 RLS，已登录客户端只能读取自己的权益；普通客户端角色没有新增、修改或删除权限，避免用户自行把账号提权。权益写入留给服务端管理工具与后续 StoreKit 收据验证流程。
- 增加 `set_account_entitlement` 服务端发放入口，可创建、更新或撤销账户权益；函数执行权限只授予 `service_role`，不向匿名、登录客户端或普通用户开放。未来管理员工具/支付回调应由可信服务使用该入口。
- 权益与 RLS 迁移尚未应用到 Supabase；当前线上用户行为没有变化。应用迁移前的旧环境仍走兼容逻辑，迁移应用后则由权益表和 RLS 决定是否允许访问。
- iOS 已增加 Supabase 只读权益请求和按账号隔离的本机缓存；登录后先验证权益，再开放业务界面。账号切换/登出会清掉内存中的上一个账号权益；验证失败时显示本地化的重试/退出页面。当前 iOS 仅开放 `.sync`；`.cloud` 在线数据层尚未实现，因此在线版权益会提示改用 Web。
- Web 已接入同一权益表读取：`sync` 保留账号隔离的浏览器缓存与离线队列；`cloud` 只在线读写，不从离线缓存展示业务资料，也不把断网写入排进同步队列。进入云端版前会先尝试提交此前遗留的离线操作。缺少权益表时按旧账号规则回退为 `sync`。
- 新增第二个数据库迁移，为现有 `auth.users` 账号补发 `.sync` 权益，并将业务表、资料表和私有图片 Storage 的 RLS 同时限制为“当前用户自己的记录 + 有效云端权益”。客户端不能自行授予或修改权益。未授权、过期或撤销账号不能通过 Supabase API 读写云数据。
- 新增账号开通契约 `set_account_entitlement`，由受信任的服务端使用 Supabase `service_role` 调用；注册 API 不会自动给用户升级或赠送试用期。默认版本、试用时长和价格确定后，再接注册后的自动开通/StoreKit 验证。
- 上述权益迁移尚未应用到 Supabase。应用前必须先落实新账号的服务端开通流程（当前无权益行会被拒绝），并在开发环境核对现有账号权益、跨账号隔离、无权益账号读写均被拒绝。未完成之前不要部署迁移，也不要把 Web 的客户端版本判断视为收费边界。
- 新账号的默认版本、免费试用与订阅价格仍未决定；当前代码没有自动赠送权益。设备上限字段已预留，但还未实施设备登记和数量限制。
- iOS 与 Web 客户端已加入权益读取；还没有真机/浏览器针对真实权益记录完成验证，且服务端迁移尚未生效，所以不能据此认定线上权限已受控。

## 下一步：iOS 在线版数据路线

服务端权益读取和开通入口已写入客户端/迁移脚本，但迁移没有应用到 Supabase。现有账号迁移后会保留为 `.sync`；新账号须由受信任服务明确开通，且默认权益/试用规则未决定。iOS 已加入不带离线队列的账号绑定 Supabase repository：客户目录读取会合并当前账号的客户、联系方式、地址；创建/编辑与删除分别使用原子 RPC，失败时不会向本机队列写入操作。新增仅驻留内存的客户目录状态模型，切换账号时先清除前一账号列表。客户页面现按 `.cloud` 权益切换到在线列表、搜索/筛选、详情和基本资料增删改，并加入账号私有头像上传/显示与按客户 UUID 读取关联行程；贡献按币种分组显示总收入和未收款。旅行社目录现有账号范围读取、保存、软删除 API 和在线页面，云端版本从首页合作旅行社入口使用独立内存状态；本机和同步版本仍走原页面。行程、停靠点、费用的账号校验读取、父子合并、一次性保存/删除 API 已接入客户端，迁移脚本中补了同事务 RPC；在线行程列表、详情、增改删表单也已切入独立内存模型，并从当前账号云端设置读取币种，航班号限制为大写 ASCII 英文和数字。钱包与名片现使用账号绑定在线资产路径，二维码/头像内容放入账号私有 Storage，编辑草稿留在内存，点击保存并收到云端确认后才完成保存。首页 `.cloud` 汇总也切为直接读取云端行程，不再走 SwiftData，并提供待执行行程和云端行程入口。数据库迁移未应用，在线页面尚未真机验收。设备 SDK 构建通过。

### iOS 在线版实施约束

- 目前 iOS 客户、行程、旅行社、名片和钱包等主要页面直接通过 SwiftData `@Query` 读取数据，并在视图中直接编辑模型；仅停用同步不能实现在线版，反而可能让界面显示保存成功但云端没有记录。
- 在在线版数据层完成前，iOS 对 `.cloud` 权益继续显示“使用 Web”提示，不开放本机业务库供该账号编辑。`.sync` 继续使用当前账号隔离的 SwiftData 云端缓存和双向同步路线；单机版继续使用本机库。
- iOS 在线版改造按以下次序进行：① 定义业务 DTO 和 Supabase 在线读写 API（不含离线队列，已完成客户目录读取及客户/联系方式/地址原子创建、编辑、删除接口）；② 将客户/联系方式/地址页面读写迁入 repository，并要求写入得到云端成功确认后才更新界面缓存；③ 以同样模式迁移旅行社、行程/停靠点/费用；④ 迁移名片、收款方式和图片对象存储；⑤ 按 `.cloud`/`.sync` 分别连入视图并验证断网时在线版不保留待上传变更、同步版离线队列正常；⑥ 在真机吴泽华的 iPhone 上验证账号隔离和写入/删除闭环。
- 不把 `.cloud` 在线路线复用为 `.sync` 的上传逻辑：同步版需要缓存、重放和冲突处理；在线版写操作必须由服务端确认后才算完成。这样可以避免两个产品版本的断网行为互相污染。
