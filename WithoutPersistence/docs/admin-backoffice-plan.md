# 统一应用管理后台：实施建议

日期：2026-11-11。状态：方案草稿，尚未开发或部署，不授权任何生产权限变更。

依据：admin-backoffice-requirements.md、account-roles.md、当前 codex/billing-1.1 / iOS 1.1(14)。保留现有未提交工作。

## 产品定位与一期范围

独立 Web 管理后台，支持桌面和平板。与用户业务 Web 分开构建、路由、部署和登录权限；共用视觉规范，不复用业务用户会话作为管理员授权。不是在普通用户页面隐藏一个管理员按钮。

一期页面：
1. 总览：当前应用/环境、账号数、有效/试用/到期/暂停数量、临近到期与设备满额提示。有效性同时判断状态与到期时间；最后活动不称为实时在线。
2. 应用：应用登记与选择，首个为云盛行程管家。接入第二个应用须部署可信连接器与产品映射，不能只填任意 URL 即访问后端。
3. 用户：分页搜索、注册时间、账号用途标签（业务/审核/开发测试/普通），状态和授权来源。标签不授予管理员权限。
4. 用户详情：授权版本/到期/设备额度、当前有效权限、设备与最后活动、手工授权与已验签订阅分别显示；不默认查询客户电话、行程正文或附件。
5. 操作：释放选中设备、延长或设置授权、暂停/恢复；先展示应用、环境、账号和影响，再确认。设备释放与 Auth 会话撤销分开；一期先交付设备释放，不提供含糊的“一键全部退出”。
6. 审计：操作者、作用域、原因、前后值、请求 ID、成功/失败、时间。首次管理员启用、权限变更也留痕。禁止密钥、密码和原始交易签名进入日志。

一期不做：账号永久删除、代用户登录、修改用户密码、读取业务内容、收费启用、退款操作、自动批量延期、把沙盒交易视为生产收入。

## 界面结构

顶栏：应用选择 / 环境标记 / 管理员。
左栏：总览、应用、用户、授权、设备、订阅（一期只读）、操作日志。
用户详情优先用侧面板与分区，宽屏横向排列；重要写操作用简洁确认框，避免长表单弹窗。
审核账号显示专用标签、可用设备名额与到期提示。当前审核账号释放后为 0/4，到期 2026-11-17 05:43:43.771423+00；后台不得自动延期。

## 技术边界

- 前端：独立目录与独立发布包；沿用现有 Web 视觉和轻量组件，先不为管理后台重写业务 Web。
- 后端：复用当前 Supabase Edge Functions / PostgreSQL 路径，新增独立管理 API；前端只持有普通管理员会话，绝不下发 service-role。
- 管理身份：单独登记管理员，首期仅所有者；默认只读角色，写权限按应用与环境授予。管理员需具备二次验证，敏感写操作验证近期认证。首次管理员由受控脚本/迁移显式建立，不自动把首个注册者、某个邮箱字符串或 user_metadata 当管理员。
- 服务端从已验证会话确定操作者，再查管理员角色与应用范围；客户端提交的 app_id/owner_id 仅是请求参数，不能决定权限。
- 凭据仅在可信服务端保管。跨项目时使用限定目的的连接器，不接受用户输入任意目标地址，避免服务端越权访问。
- 写入采用事务、预期版本或前后值校验与幂等请求 ID；设备操作沿用注册路径的账号锁，防并发登录/重复点击。
- 数据变更和成功审计同事务提交；失败日志有独立受限记录路径。服务角色只能由受控 API 使用，不能因“内部后台”放宽现有 RLS。

## 多应用模型与兼容

管理平台建议模型：applications、application_environments、admin_principals、admin_role_bindings、application_accounts、admin_audit_events。
应用账号唯一键为 (application_id, environment_id, source_user_id)；邮箱用于显示和搜索，不用于跨项目合并身份。管理员身份与业务账号、客户联系人分开。

TrvelMA 现有 account_entitlements / account_devices 只按 owner_id 建模，因此一期采用应用连接器适配，不立即给所有线上业务表补 app_id。未来应用可独立后端；若确需共享业务数据库，再单独迁移多应用隔离键与 RLS，不能只在管理界面加应用选择就宣称数据已隔离。

扩展阶段追加 customer_organizations、memberships、feature_definitions、plans、scoped_grants、quota_policies；客户组织是购买方，不是行程里的乘客/客户联系人。

## 授权规则

当前 set_account_entitlement 是服务端授权入口；Apple 台账包含 baseline/last_written_grant，不能绕过既有撤销优先和手工授权保留规则，也不能改写已验签交易来制造订阅。
一期对现有账号授权做兼容包装，变更前核对手工/试用/订阅来源，并测试延迟 Apple 通知不会覆盖新的管理变更。

后续定制授权顺序建议：账号/组织停用优先拒绝；基础方案给出默认能力；有范围和有效期的客户例外覆盖；硬性平台禁用优先拒绝。额度按明确作用域计算，不默认把多个来源相加；永久使用权不代表无限航班查询。
未完成服务端模块权限与额度执行前，后台不得提供看似有效的开关。现有个人账号保持个人归属，不自动改成企业成员；Apple 购买归属保持原账号，不自动转给组织。

## 迁移、上线与回滚

阶段 A：隔离原型与接口契约，合成账号、第二个合成应用，完成布局评审，不接生产写权限。
阶段 B：管理身份、最小只读 API 和新增管理表；保留当前业务模型。测试库验证迁移/回滚，再申请正式部署授权。
阶段 C：上线只读后台，核对三类指定账号及授权/设备/交易来源；禁止从前端直连 Auth 管理接口。
阶段 D：逐项启用设备释放、授权调整，包含确认、幂等、审计和并发测试；启用生产管理入口需明确授权。
阶段 E：企业客户、员工与客户定制授权，按服务端实际能力逐项接入。

新增表不修改现有业务表数据；迁移前留存目标结构与权限快照。回滚先关闭管理写入口、撤销管理 API 权限、恢复旧前端；审计记录保留。已发生的授权变更只能按审计执行有条件的补偿操作，不用 DROP TABLE 或批量还原覆盖后续合法变化。实际 SQL、连接器权限和备份恢复步骤须在阶段 B 实施时交付。

## 验收门槛

- 未登录/普通账号/被撤销管理员均无法调用管理 API；直接伪造参数也失败。
- 应用 A 管理员不能读写 B；开发环境不能操作生产，使用第二个合成应用验证。
- 设备释放只影响所选账号和设备；并发注册、过期选择、重复请求不误伤。
- 授权延长/暂停/恢复生效与现有 App/Web 一致；存储 active 但已过期时仍显示无效。
- 手工授权、订阅、撤销、到期以及延迟/乱序 Apple 通知交互通过隔离测试；正式收费开关不变。
- 事务失败无“成功”审计假象；成功动作可追溯，无密码/Token/密钥泄露。
- 静态发布包不含服务密钥；部署后最小权限实测，普通业务账户不参与变更验收。
- 上线前确认管理员本人、二次验证与恢复方式、平台部署项目、审计保留期限及管理员数据可见范围。
