# 需求 3：接机航班起飞跟踪与通知

状态：已实现，待部署和真机推送验收。

适用于已选定航段且待执行的接机行程。起飞跟踪与需求 1 的落地排程各自运行，送机及其他行程类型不触发。按已选航段查询，同航段可共用查询，各订单通知使用各自的客人名称。

| 查询结果或时点 | 行为 |
| --- | --- |
| 原计划起飞时间后 2 分钟 | 首次读取起飞状态。 |
| 尚未起飞且航司未明确报告延误 | 从本次查询起 1 小时后再查一次，此时不发延误通知。 |
| 航司明确报告延误，且有新的预计起飞时间 | 立即发送延误通知，按最新预计起飞时间延后 2 分钟安排唯一一次复查（尚未使用时）。 |
| 航司明确报告延误，预计起飞时间待定 | 立即发送延误通知，写明「预计起飞时间待定」，1 小时后复查（尚未使用时）。 |
| 已确认起飞 | 发送起飞通知，记录实际起飞时间并结束起飞跟踪，落地排程继续。 |

- 每个航段的自动起飞查询最多两次，即首查一次、复查最多一次。复查尚未执行时，可按更新的预计起飞时间改期。复查后仍未确认起飞，保留最近状态并标记「起飞待确认」，可手动刷新，不再增加自动查询。
- 起飞最多两次、落地最多两次，每个航段合计最多四次自动查询，按当前每次 50 积分估算上限 200 积分。手动查询另计。
- 推送标题统一为「航班管家」。
- 延误通知包含客人名称、航班号、起飞机场，以及最新预计起飞时间或「待定」，仅在航司明确报告延误时发送。
- 起飞通知包含客人名称、航班号与起飞机场当地的实际起飞时间。若航班有延误，显示实际起飞减最初计划起飞所得的延误时长。预计空中飞行时长由最新预计到达减实际起飞计算，两端时间先转换到同一时区。
- 接口缺少时长计算所需字段时，省略相应时长。查询和通知不修改订单约定的接客时间。


## 发布与回滚

- 起飞和落地共用现有航班 Cron 入口，先升级数据库、再部署任务函数。消息会写入各账号独立的「航班管家」收件箱，iOS 和 Web 都可读取。
- 系统推送需要给主 App ID 启用 Apple Push Notifications，并使用带推送授权的签名描述文件。归档时传入 `TRVELMA_PUSH_ENTITLEMENTS=scripts/flight-push.entitlements`；TestFlight/正式版设 `TRVELMA_APNS_ENVIRONMENT=production`，Debug 真机调试用 `development`。部署私有 Edge secrets `FLIGHT_APNS_PRIVATE_KEY`、`FLIGHT_APNS_KEY_ID`、`FLIGHT_APNS_TEAM_ID` 后，用独立测试账号开启航班推送并验收。禁止在源码或日志中放入密钥。
- 停用 APNs 发件时移除 Edge 上对应推送密钥配置，已入收件箱的消息保留。回滚起飞排程时可恢复到只执行落地的上一版任务函数，保留已有起飞记录。
